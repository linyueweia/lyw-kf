# 媒体簇对标例外清单（tools/r5s-media-parity.py 读取）
#
# 判据：K1 与官方 R5S 同为 RK3568，媒体簇必须与官方件 dist/rk3568-nanopi-r5s-official.dtb
#       （飞牛官方 R5S 固件内那份，sha256 95d4f336ce4d5268bf1f950a51d10ad8d3b13fd75eb9f8a079d90dc9671f8ed7）
#       逐节点一致。下列差异是【本板有实机证据的故意保留】，新增前必须补齐同样的证据。
#
# 格式：<missing|extra|diff|missing-prop|extra-prop> <节点路径或节点名> [属性名]
#
# ── 1. 不新增 vdpu@fdea0400（官方有，本板故意没有）──────────────────────────
# 官方 R5S 同时挂着两代解码节点：video-codec@fdea0400(rockchip,rk3568-vpu) 与
# vdpu@fdea0400(rockchip,vpu-decoder-v2)，两者寄存器区间重叠（0xfdea0400 落在
# 0xfdea0000+0x800 内）。本板目前只挂 legacy 那份，且 2026-10-19 实机已验收
# 「ffmpeg -c:v hevc_rkmpp 解码 + hevc→h264 转码 EXIT=0、resetting 风暴 0」。
# 新增第二份会让同一硬件被两个 mpp 客户端争用 —— 正是 10-19 转码死机那一类风险，
# 必须先上机验证（判据：/sys/kernel/debug/mpp_service 只有一个 vdpu 实例、
# rkvdec 中断正常增长、无 mpp_task_timeout）再解除本条。
missing vdpu@fdea0400

# ── 2. ~~NPU 的 iommu@fde4b000 保持 disabled~~ 【2026-10-27 已撤销：改回 okay】
# 旧结论（2026-10-12）：pm_domain 等不到 npu 域 ACK → iommu probe 被挡 → rknpu -EINVAL，
#   于是走 non-iommu 逃生门（img2vec 小模型可通过）。
# 翻案（2026-10-27，新内核 6.18.18.c1145-trim + 本 DTB 实机）：
#   改回 okay 后 iommu 正常 probe（/sys/class/iommu/fde4b000.iommu、iommu_group/8），
#   dmesg「rknpu iommu is enabled, using iommu mode」，NPU 中断 0→1428，零分配失败。
#   冷启动仍会打一次 ack 超时，但 genpd Forcing sync_state() 后 iommu 正常起来。
#   决定性收益：iommu 模式 GEM 走 scatter-gather 吃系统内存，不再受 CMA 256M 限制
#   （non-iommu 下 trim.face_det 要 339MiB 连续 CMA，必失败）。
#   因此本节点**不再允许与官方存在 status 差异**，下面这条 allowlist 条目已删除。

# ── 3. GPU OPP 表多两个分档变体（官方表没有）────────────────────────────────
# 本板 dump 自带的 opp-j-600000000 / opp-m-800000000 是同一 SoC 的速度分档变体，
# 每条都带 opp-supported-hw，未命中的档位内核会自行过滤，不影响选频；删除会让
# 低档位芯片失去对应电压点，故保留。
extra opp-table-1/opp-j-600000000
extra opp-table-1/opp-m-800000000
# NPU OPP 表同理（本板 dump 自带的分档变体）
extra npu-opp-table/opp-j-600000000
extra npu-opp-table/opp-m-900000000
